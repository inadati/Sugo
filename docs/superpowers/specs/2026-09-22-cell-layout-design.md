# セルレイアウトの自動整列と MCP からの操作

- 日付: 2026-09-22
- 対象: sugo-gui / sugo-infra / sugo-mcp

## 背景と問題

ハーネスを新規作成して開くと、全セルが横一列に並ぶ。`sugo-gui/src/components/BoardGraph.vue` の
dagre 設定が `rankDir: "LR"` であり、分岐のない直線ハーネスでは層が一方向に伸び続けるためである。

結果として次の不具合が生じる。

- グラフ全体を表示領域に収めようとして倍率が下がり、セル名の文字が読めないほど小さくなる
- 離れたセルを結ぶエッジが長く伸び、他のエッジと重なって経路を追えない

現状これを解消する手段は、ユーザーがノードを一つずつドラッグして並べ直すことだけである。
セル数が多いハーネスではこの作業が現実的でない。

さらに二つの構造的な問題がある。

1. **座標が localStorage にしかない**（`BoardGraph.vue` の `lsKey()` / `savePositions()`）。
   sugo-mcp は別プロセスの Rust サーバーであり、座標を読むことも書くこともできない。
2. **初回の自動配置結果が永続化され、以後ずっと再利用される**（`placeNodes()`）。
   dagre の設定を修正しても、既存ハーネスは横一列のまま表示され続ける。UI に再整列の手段もない。

## 目標

- ハーネスを開いた時点で、人手を介さず読みやすい配置になっていること
- 配置が不適切だった場合に、MCP 経由で Claude が修正できること
- レイアウトが決定的であること（同じ盤面からは常に同じ配置）

## 非目標

- エッジ交差ゼロの保証。交差数最小化は NP 困難であり、平面描画できないグラフも存在する。
  本設計が保証するのは「折り返しによって交差数を悪化させないこと」である。
- 既存 localStorage 座標の移行。座標は盤面から再計算可能であり、
  そこに保存されている横一列こそが解消対象であるため、移行せず破棄する。

## 方式

### 座標の置き場所

SQLite に専用テーブルを新設する。

```sql
CREATE TABLE IF NOT EXISTS cell_positions (
  harness_id TEXT NOT NULL REFERENCES harnesses(id),
  cell_id    TEXT NOT NULL,
  x          REAL NOT NULL,
  y          REAL NOT NULL,
  PRIMARY KEY (harness_id, cell_id)
);
```

`board_versions` の `definition_json` には入れない。座標は盤面の意味論ではなく表示上の情報であり、
不変 JSON に混ぜると座標を動かすたびに新しい board version が切られ `content_hash` も変化する。
run は board_version にピン留めされるため、表示の変更が実行状態に波及する。別テーブルが正しい境界である。

sugo-mcp と sugo-gui は `sugo_infra::paths::default_db_path()` で同一の SQLite ファイルを共有しており、
このテーブルが両者の連絡路となる。

### レイアウト計算の所在

計算は GUI 側（TypeScript / elkjs）に一本化する。ELK の layered アルゴリズムに匹敵する
層割り当てと交差最小化を Rust で再実装するのは労力に見合わない。

MCP から全体整列を依頼する場合は、**該当ハーネスの `cell_positions` 行を削除する**。
「座標が無いセルは自動配置に回る」という規則が既に `placeNodes()` にあるため、
削除すれば次の描画で全体が組み直される。専用のフラグや通知経路は設けない。

| 責務 | 担当 |
|---|---|
| レイアウトの計算 | sugo-gui（elkjs + 蛇行後処理） |
| 座標の永続化 | SQLite `cell_positions` |
| 座標の読み取り・個別修正 | sugo-mcp |
| 全体整列の依頼 | sugo-mcp（座標を削除する） |

### 蛇行レイアウトのアルゴリズム

ELK の `wrapping` 機能は使わない。ELK は出力に層の情報を含まず、座標から行の切れ目を
復元することができないためである。実測では分岐のあるグラフで同一行内のノードが
異なる y 座標（y=101 と y=128）に配置され、行の境界を座標から判別できないことを確認した。
行が確定できなければ「奇数行を反転する」後処理が成立しない。

そこで ELK には層割り当てと交差の少ないノード順序の決定のみを担当させ、
折り返しは自前で行う。

1. ELK layered を `direction: RIGHT`、`wrapping: OFF` で実行する
2. 層を識別する。direction=RIGHT の layered 出力では同一層のノードが同一の x に揃う
3. 層を K 個ずつの行に区切る。K は結果の縦横比が目標値（1.6）に最も近くなる値を、
   1..層数 の全探索で選ぶ
4. 各行を縦方向に積む
5. 奇数行は行内で x 座標を左右反転する（`x' = rowMinX + rowMaxX - x`）

手順 5 により行の進行方向が交互に反転し、行末から次の行頭へのエッジが
横断する長い線ではなく真下への短い線になる。

全手順が決定的であり、同一の盤面からは常に同一の座標が得られる。

### モジュール構成

蛇行レイアウトは `sugo-gui/src/lib/layout.ts` に純粋関数として実装する。

- 入力: セル一覧（id・寸法）、エッジ一覧、目標縦横比
- 出力: 座標マップ `Record<cellId, {x, y}>`
- cytoscape・Tauri・DB のいずれにも依存しない

この分離により、レイアウトの質を単体テストで直接検証できる。
`BoardGraph.vue` は座標マップを受け取って cytoscape に適用する役割に限定される。

### MCP ツール

| ツール | 引数 | 役割 |
|---|---|---|
| `sugo_get_layout` | `harness_id` | 全セルの座標・寸法とエッジを返す。未配置セルは座標 `null` |
| `sugo_set_layout` | `harness_id`, `positions[]` | 指定セルの座標を上書きする |
| `sugo_relayout` | `harness_id` | 該当ハーネスの座標を全削除する |

`board_versions` を変更しないため版は上がらず、楽観ロックも掛けない。
表示上の情報であり後勝ちで支障がない。

`sugo_set_layout` は盤面に存在しない `cell_id` を指定された場合エラーを返す。

### GUI の挙動

`placeNodes()` の判断構造は維持し、保存先のみ localStorage から Tauri コマンド経由の DB に差し替える。

- 座標が一つも無い（新規ハーネス）→ 全体を自動レイアウトして保存
- 一部だけ無い（セルを追加した）→ 既存セルは動かさず、新規セルのみ追加配置
- どのセルにも座標がある → そのまま適用

ツールバーに「整列」ボタンを新設する。押すと全体を組み直して保存する。
ドラッグによる手動調整とその永続化は従来どおり維持する。

座標の保存は「該当ハーネスの行を全削除してから現在のノード分を挿入」を単一トランザクションで行う。
これにより削除済みセルの座標が残留しない。ハーネス削除時には座標も併せて削除する。

## テスト方針

### レイアウトエンジン（`layout.ts`）

elkjs は Node 上で動作するためモックせず実物を使う。

- **決定性**: 同一の盤面を2回処理して座標が完全に一致すること
- **蛇行**: 一本鎖24マスで行ごとに進行方向が反転すること
- **縦横比**: 折り返し後の縦横比が閾値以下に収まること
- **交差数**: 折り返し前後で線分交差数を数え、増加していないこと

4つ目は「素朴な折り返しは交差を増やす」というリスクを数値で押さえるためのものであり、
本設計で最も重要な検証である。

### 永続化層

`sugo-infra/tests/sqlite_repository.rs` の既存の流儀に従う。

- 座標の保存と読み出しが往復すること
- 保存が全置換であり、削除済みセルの座標が残らないこと
- ハーネス削除で座標も削除されること

### MCP ツール

`sugo-mcp/src/tools.rs` の既存の流儀に従い、引数型の round-trip と必須項目欠落時のエラーを検証する。

### E2E

新規ハーネスを作成して開いたとき、配置が横一列でないことを検証する1本を追加する。

## 作業順序

各段階の終了時点でアプリが動作する状態を保つ。

1. **DB 層** — `cell_positions` のスキーマとリポジトリ（Rust・TDD）
2. **配線の差し替え** — Tauri コマンドを追加し、GUI の保存先を DB へ移す。
   レイアウト計算はこの時点では dagre のまま据え置く
3. **レイアウトエンジン** — `layout.ts` を ELK + 蛇行で実装（純粋関数・TDD）
4. **接続** — `BoardGraph.vue` を `layout.ts` に繋ぎ替え、「整列」ボタンを追加
5. **MCP ツール** — `sugo_get_layout` / `sugo_set_layout` / `sugo_relayout`
6. **仕上げ** — ハーネス削除時のカスケード、E2E

手順 2 を 3 より先に置くのは、保存先の移行とレイアウト計算の刷新を同時に行うと、
不具合発生時に原因を切り分けられなくなるためである。

## 依存の追加

`elkjs` を sugo-gui に追加する。bundled 版は約 1.4MB と軽くはないが、
層割り当てと交差最小化を自前実装する代替案は現実的でないため許容する。

## 根拠となる実測

elkjs 0.12.0 を用いて、24マスの鎖に分岐1本と後方エッジ1本を加えたグラフで検証した。
この検証は ELK 自身の wrapping 機能を用いた**折り返しの効果の確認**であり、
採用するアルゴリズムそのものの測定ではない。

| 条件 | 寸法 | 縦横比 |
|---|---|---|
| 折り返しなし | 3592 x 155 | 23.2 |
| 折り返しあり | 1142 x 460 | 2.5 |

折り返しによって縦横比が一桁改善することを確認した。
分岐のない一本鎖24マスでは4マスずつ6行に折り返された。

同時に、ELK の wrapping 出力では分岐を含む行の境界を座標から判別できないことも確認した。
これが「ELK の wrapping を使わず折り返しを自前で持つ」という判断の根拠である。
自前実装では行数を直接制御するため、縦横比は目標値（1.6）付近に収束させられる。
上表の 2.5 は ELK の自動折り返し位置決定による結果であり、目標値とは一致しない。
